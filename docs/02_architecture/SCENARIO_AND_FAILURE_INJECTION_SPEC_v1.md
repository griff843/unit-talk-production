# Scenario and Failure Injection — Specification

Version: 1.1 Status: Canonical Authority: Architecture Layer Phase: R3 (Shadow
Mode) — COMPLETE | R4 (Fault Injection) — IN PROGRESS Sprint:
SPRINT-VERIFICATION-SHADOW-DIVERGENCE-GUARDRAILS

This document defines the architecture and specification for shadow mode (R3)
and fault injection (R4) in the Unit Talk Verification & Simulation Control
Plane.

---

# 1. Purpose

Shadow mode and fault injection extend the verification infrastructure beyond
deterministic replay to cover two additional risk surfaces:

**Shadow Mode (R3)**: Does the pipeline produce the same results as production
when running in parallel with live data and suppressed side effects?

**Fault Injection (R4)**: Does the pipeline behave correctly under controlled
failure conditions — provider timeouts, write failures, clock skew, partial
data?

Together these phases provide evidence for:

- safe canary promotion of autopilot changes
- validated freeze rule behavior under real failure conditions
- demonstrated resilience of lifecycle enforcement under pressure

# 2. Shadow Mode (R3)

**Status: COMPLETE** **Verified by**:
SPRINT-VERIFICATION-SHADOW-DIVERGENCE-GUARDRAILS

## 2.1 Architecture Intent

Shadow mode runs the pipeline using live data (read-only Supabase access) with
all side effects suppressed. The shadow run produces lifecycle traces that can
be compared against production behavior.

```
Production pipeline (live)  ←→  Shadow pipeline (side-effect-free)
         │                                │
         ▼                                ▼
   production traces              shadow traces
         │                                │
         └──────────── diff ──────────────┘
                         │
              behavioral match / divergence report
```

## 2.2 Implemented Infrastructure

The following components are implemented in
`apps/api/src/lib/verification/shadow/`:

- `types.ts` — shared types for shadow run inputs, divergences, and verdicts
- `shadow-comparator.ts` — compares shadow lifecycle traces against production
  traces for the same event sequence
- `divergence-classifier.ts` — classifies divergences by severity (CRITICAL /
  HIGH / LOW)
- `shadow-verdict.ts` — emits PASS / PASS_WITH_WARNINGS / FAIL verdict based on
  divergence set
- `shadow-proof-writer.ts` — writes proof bundles to `out/shadow-runs/<run-id>/`
- `shadow-runner.ts` — orchestrates a full shadow comparison run
- `index.ts` — public module exports

Side-effect suppression adapters (established in R1, used by R3):

- `recording-publish.ts` — records publish attempts without Discord calls
- `null-notification.ts` — suppresses all operator notifications; captures
  critical divergence alerts
- `recording-recap.ts` — records recap outputs without delivery
- `RunController` validates shadow mode adapter set

CLI runner:

- `scripts/run-shadow-guardrails.ts` — standalone guardrail runner

Tests (35 new verification tests):

- `divergence-classifier.test.ts` — 15 tests
- `shadow-verdict.test.ts` — 11 tests
- `shadow-runner.test.ts` — 9 integration tests

## 2.3 Governance Note

R3 is complete. Shadow-mode canary safety evidence is now available via proof
bundles generated by `run-shadow-guardrails.ts`.

The governance requirement is satisfied: shadow pipeline comparison is
operational and produces traceable proof artifacts.

# 3. Fault Injection (R4)

**Status: IN PROGRESS**

## 3.1 Architecture Intent

Fault injection runs the pipeline against a controlled failure scenario. A
scenario defines one or more faults that are injected at specific points in the
event sequence:

- provider API timeout or error response
- Supabase write failure at a specific lifecycle stage
- Partial data delivery (missing fields in event payload)
- Clock skew (out-of-order event timestamps)
- Duplicate event injection (idempotency stress test)

## 3.2 Foundation Already in Place

- `ExecutionMode = 'fault'` defined
- Adapter layer supports fault-mode routing (adapters can be instructed to
  simulate failures)
- `RunController` validates fault mode adapter set

## 3.3 Remaining Work

The following components are not yet complete:

- **Fault scenario definition format**: Structured definition of failure
  conditions, injection points, and expected pipeline responses.
- **Fault scenario library**: Library of pre-defined fault scenarios covering
  key failure modes.
- **Fault injection adapter variants**: Adapter implementations that simulate
  specific failure conditions (e.g., `failing-publish-adapter.ts`,
  `timeout-settlement-adapter.ts`).
- **Fault proof bundle structure**: Proof bundle format for fault runs,
  including which faults were injected and how the pipeline responded.

## 3.4 Freeze Rule Validation

Fault injection is the mechanism for validating the `AUTOPILOT_FREEZE_MATRIX`
under real failure conditions. Scenarios must include at minimum:

- provider data unavailable
- settlement service unreachable
- scoring output missing

The pipeline must demonstrate fail-closed behavior under each of these scenarios
before fault injection can be declared complete.

---

# 4. What Shadow and Fault Do NOT Prove

- **Shadow mode** does not prove live provider truth. It reads production data
  but does not verify that the provider is returning fresh, valid data.
- **Fault injection** does not prove that every possible failure mode has been
  covered. It proves the specific scenarios that were defined and injected.
- Neither mode proves production delivery (Discord posts, notifications).

# 5. Scenario Definition (Design, Not Yet Implemented)

The following is the intended fault scenario definition format.

This is **designed but not yet implemented**:

```typescript
interface FaultScenario {
  scenarioId: string;
  description: string;
  faults: FaultDefinition[];
}

interface FaultDefinition {
  targetAdapter: 'publish' | 'feed' | 'settlement' | 'notification' | 'recap';
  triggerAtSequenceNumber: number;
  faultType:
    | 'timeout'
    | 'error'
    | 'partial_data'
    | 'duplicate_event'
    | 'clock_skew';
  faultPayload?: Record<string, unknown>;
  expectedPipelineResponse:
    | 'fail_closed'
    | 'retry'
    | 'skip'
    | 'propagate_error';
}
```

When R4 is implemented, fault scenarios will be defined in the `test-fixtures/`
directory and runnable via the CLI.
